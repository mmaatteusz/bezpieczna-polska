## Backend — mocne strony

1. **Fail-closed** przy zmianach kontraktu źródła.
2. Ostatnia poprawna kopia danych jest zachowywana zamiast czyszczenia danych przy błędzie.
3. Oddzielny `source health` z last success, last attempt, errorCode i świeżością.
4. PostGIS jest wymagany w production.
5. `/ready` faktycznie sprawdza bazę i schemat.
6. Precyzyjne współrzędne są wysyłane przez POST.
7. Admin API jest rate-limitowane i wymaga stałoczasowego porównania bearer tokena.
8. NEPTUN ma osobny worker 5 s.
9. Push ma kolejkę trwałą i retry.
10. Historia zdarzeń i incydentów jest wersjonowana.

## Backend — do poprawy

1. Railway powinien deployować tylko z `main`.
2. `BUILD_SHA` musi odpowiadać faktycznemu commitowi deploymentu.
3. Runtime smoke nie powinien mieć hardcodowanych historycznych SHA w repo.
4. Nieużywane serwisy i baza powinny zostać usunięte lub nazwane jako archiwalne.
5. Brakuje jednolitego blokującego testu runtime wszystkich źródeł krytycznych.
6. Produkcja nie ma własnej domeny — jest tylko domena Railway.
7. Region Railway to `sfo`; dla aplikacji głównie polskiej warto rozważyć region bliżej użytkowników, jeśli Railway oferuje odpowiednią lokalizację i migrację danych.

## Mobile — do poprawy

1. Nie wiązać release APK z backendem, który może być na starym branchu.
2. Wyświetlać jawnie różnicę między cache/offline a live.
3. Utrzymywać regresje dla mapy przy oddaleniu/przybliżeniu i przełączaniu schronień/alertów.
4. Przy błędzie źródła nie powielać identycznych komunikatów.
5. Testować instalację aktualizacji APK na urządzeniu bez deinstalacji poprzedniej wersji.
6. Release signing i Play Protect wymagają docelowej konfiguracji dystrybucyjnej.
